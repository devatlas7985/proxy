# 代理服务器基础

代理服务器在本文限定为网络代理，代理这个词不涉及商业代理商；代理ip是口语称呼，没有统一技术定义。http代理、SOCKS5 与 VPN 的相关资料在这里分别解释，不用一个对照标签补出全部机制，也不讨论代理 IP 的用途或买卖。

## 网络代理先看文档实际描述哪个对象

RFC 9110 的 CONNECT 部分讨论经代理建立隧道，RFC 1928 讨论 SOCKS5，Android 与 Apple 文档讨论各自的 VPN 接口。这些来源分别定义自己的对象，没有提供一段可直接照搬的代理与 VPN 全面对照。本文将它们并列阅读，不自造官方比较结论。

网络代理这个主题也不能仅凭服务器名称解释。某个地址被人称作代理 IP，只保留口语标签并没有确认协议、认证方法或实际经营者。本文没有具体地址，不从标签为任何资源填身份、功能或可用性。

“代理”在商业中还可以表示代理商，但本文不展开那个含义。此处只讲网络文档的代理、隧道和接口对象，也不把商业关系用于解释协议。两个中文用法相同，不会让相应定义自动互通。

阅读基础资料时，可以先保留来源名字与定义位置。协议在说明怎样通信，平台接口在说明应用能调用什么能力，两类内容需要不同主语。本文没有用一个术语替其他资料完成全部解释。

下面的问答和表格因此限于已取得的原文。没有服务名单、端口推荐或应用场景结果，也不按协议名称赋予安全、速度或匿名保证。具体记录缺少时，概念不会自动生成实例。

## HTTP CONNECT 建立的是目标隧道

RFC 9110 说明 CONNECT 让代理与目标创建隧道，成功后对两个方向的数据进行转发。目标采用主机及端口的格式，并且必须有端口；收到 2xx 成功响应后进入隧道模式。这里描述交互步骤，不是可直接使用的服务器配置。

规范还将隧道写作连接之间不修改消息的盲中继。这个用词解释该对象的转发性质，不提供一份现实代理经营者能看到哪些字段的完整清单。本文不把“盲”这个词扩大为所有信息都不可见的承诺。

目标主机与端口出现在 CONNECT 请求本身，是格式已经明确的内容。与此不同，隧道建立后的数据怎样受上层保护，需要读相应协议说明，不能由请求格式直接推断。本文没有具体请求或响应记录。

文档还提出限制 CONNECT 可用端口的规范性要求。这里仅说该要求存在，不展开端口使用场景或提供操作步骤。标准中的例子也不会被本文改造成实际地址、命令或外部资源。

对应原文用 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) 表示。它可以解释 CONNECT 隧道，不为任意叫 HTTP 代理的软件提供全部产品能力表；某个应用是否实现了哪些部分，仍需自己的说明。

## SOCKS5 用命令和协商描述通信

RFC 1928 将 SOCKS5 定位为供 TCP、UDP 应用使用网络防火墙服务的框架。它把自身放在应用层与传输层之间的概念位置，并指出不提供网络层网关的部分服务。这是文档对自己层级的描述，不是对全部 VPN 的统一反面定义。

请求命令有 CONNECT、BIND 和 UDP ASSOCIATE。UDP 关联与相应 TCP 连接有生命周期关系，TCP 结束时关联也终止；不能只见 UDP 字样就把它当成完全独立的任意网络连接。本文不补命令编码之外的实现步骤。

这些命令与认证协商又是不同部分。文档包含无需认证的方法，也说明若选定方法提供完整性、机密性封装，相关请求必须按该方法封装。本文不从“有认证”直接推出所有数据已经采取相同加密。

同样，协议本身有哪些命令，不代表某个现实服务器启用了所有命令。没有服务器声明和实际记录时，本文不为某个地址补可用能力。标准、实现和经营者三类对象保持独立。

[RFC 1928](https://www.rfc-editor.org/rfc/rfc1928) 只对应 SOCKS5 规范。它不能替一个产品页填写设备数、费用、日志或系统平台，也没有在本文形成任何资源推荐。

## 认证、封装与 TLS 的问题分别回答

SOCKS5 规范把安全性联系到协商选择的认证和封装方法。这段内容不提供一条“只要叫 SOCKS5 就有统一机密性”的结论。本文也不填未取得原文的用户名密码方法细节，避免把另一个标准内容借过来。

TLS 1.3 的设计目标包括防窃听、篡改与消息伪造。它的机密性说明针对通道建立后发送的数据，并将可见范围限定为通信两端；这里的条件不能被省成任何网络内容都不可见。协议性质仍有适用对象。

同一规范明确不会隐藏所传数据的长度。因此，通道机密性与所有信息隐藏不是同一句话，本文不加入隐藏行踪、匿名身份等承诺。它也不根据某个项目宣称 TLS 就替实际连接确认已正确建立。

[RFC 8446](https://www.rfc-editor.org/rfc/rfc8446) 对应这份 TLS 原文。本文没有实际握手、证书或数据包记录，不判断某个中间方具体能读取什么。规范中的端点与现实经营主体之间，也没有由本文补一张自动映射表。

认证回答怎样被允许通信，封装与通道保护又有自己的文档。它们可以在一个系统中同时涉及，但不能互相替代证据。没有具体实现说明时，本文保留各段原有范围。

## VPN 平台接口按 Android 与 Apple 分别读

Android VpnService 是应用用来扩展、建立 VPN 方案的系统基础类。它能建立虚拟网络接口、配置地址和路由，再向应用返回文件描述符，用于读写 IP 数据包并经隧道与远端交换。这个接口的功能说明不等于它已经提供某个商业服务。

文档说明应用第一次建立 VPN 连接需要用户操作，系统同时活动的 VPN 连接数量为 1，并由系统显示通知。这些是接口相关的系统条件，不是某个具体应用的完整菜单。本文没有据它们编客户端安装或授权截图。

Apple NEVPNManager 则用于创建、管理 iOS 与 macOS 的 Personal VPN 配置。文档描述典型用途是在公共 Wi-Fi 之类不安全网络环境中保护浏览活动；它没有直接列出本文所有网络代理对象的比较结果。平台概念不会替产品补方案条款。

[Android VpnService 官方文档](https://developer.android.com/reference/android/net/VpnService)、[Apple NEVPNManager 官方文档](https://developer.apple.com/documentation/networkextension/nevpnmanager) 对应两套文档。这里保留各自接口定义，不从 Android 的限制去给 Apple 写同样状态，也不把 Apple 的场景用来判断所有代理实现。

两套接口都不是本文执行过的操作。没有设备、应用和配置资料，不能说连接已建、系统已授权或流量已经按某路径处理。平台有能力与实例已运行，仍是两个不同判断。

## 层级对照只复述来源，不作官方总比较

OpenVPN 的官方说明将其描述为使用 SSL/TLS 的网络扩展，明确写不是在网页浏览器运行的网页应用代理。SOCKS5 的文档说概念上在应用与传输层之间，Android 则说明接口数据包从 IP 头开始。它们是不同文档各自的表述，不是一份共同发表的比较定义。

| 来源对象 | 原文可以确认的描述 | 本文不附加的结论 |
| --- | --- | --- |
| HTTP CONNECT | 与目标建立隧道后双向转发 | 任意软件全部能力 |
| SOCKS5 | 应用与传输之间的框架、含 TCP 与 UDP | 所有实现相同保护 |
| TLS | 建立后通道机密性及长度边界 | 所有信息或身份被隐藏 |
| Android 接口 | 虚拟网络接口与 IP 数据包 | 某应用当前已正确运行 |
| Apple 接口 | Personal VPN 配置管理 | 一份代理与 VPN 总对照 |

这张表以来源对象作行，而不是按产品评定数值。它没有把层级名称转成某一方式优于另一方式，也没有用单段规范解释所有网络架构。各行能回答的内容继续限定于原文。

尤其是“代理和 VPN 有什么不同”这个问法，本文没有一份官方直接对照句可引用。能够做的是保存上述定义，再明确资料尚未涵盖的部分。不能因为读者希望一行答案，就把相邻事实拼成来源未写的总括。

代理 IP 也不在这些标准中构成一个统一产品类别。本文只把它作为口语说法，不谈它的用途、交易、选择或供应来源。术语出现不增加任何真实地址或服务信息。

## FAQ

### 代理就是商业代理商吗？

本文限定网络代理含义。商业语境的同名用法不参与这里的协议解释。

### CONNECT 成功后发生什么？

规范说明成功响应后进入隧道模式并转发双向数据。本文没有实际请求结果，也不把定义写成连接已成功。

### SOCKS5 都自带同一种加密吗？

原文将安全性关联到认证与封装的协商。本文没有把协议名转换为统一加密保证。

### TLS 会隐藏所有信息吗？

规范明确不隐藏数据长度。通道机密性不能扩大成全部信息或身份都被隐藏。

### 系统有 VPN 接口就等于提供服务吗？

接口说明平台为应用提供什么能力。具体应用与远端服务交付需要另有资料。

### 官方有一句代理与 VPN 的总区别吗？

所用文档未给直接对照句。本文分别保留定义，不声称它们共同得出统一总比较。

### 代理 IP 在这里有标准产品定义吗？

本文把它作为口语说法。没有为它补统一用途、规格或交易说明。

### 这份资料能判断某个代理地址安全吗？
